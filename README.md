# Inventory Web App

Npm + Express app that stores items in a JSON file and provides a spreadsheet-like UI, a
drag-and-drop project schematic editor, personal equipment loan tracking, and per-item photos.

Run locally:

```bash
npm install
npm start
```

Open http://localhost:3000

By default there is no login wall (handy for local dev). Set `APP_PASSWORD` to enable one — see
[Deploying to Render](#deploying-to-render) below.

## APIs

- `GET /api/items` — list items
- `POST /api/items` — add item (json: name, storagePlace, amount, type, project, availability, photo)
  - `type` may be one of the presets: `wire roll`, `cable`, `speaker`, `microphone`, `micro-controller`, `instrument`.
- `PUT /api/items/:id` — update
- `POST /api/items/:id/photo` — upload a photo for an item (multipart form field `photo`; JPEG/PNG/WEBP/GIF, max 5MB)
- `POST /api/items/:id/remove` — remove quantity (json: amount)
- `POST /api/items/:id/borrow` — borrow (decrements amount)
- `POST /api/items/:id/return` — return (increments amount)
- `POST /api/items/:id/transfer` — send quantity to another project
- `GET /api/locations` — list known storage locations
- `POST /api/locations` — add a storage location (json: { name })
- `GET /api/viz/:project` / `PUT /api/viz/:project` — shared schematic layout, connections and
  splits for a project (used by the schematic editor so all collaborators see the same diagram)
- `GET /api/loans` — list personal equipment loans
- `POST /api/loans` — check out equipment to someone outside of any project (json: itemId, borrower, quantity, expectedReturn, notes)
- `POST /api/loans/:id/return` — mark a personal loan as returned

## UI

- Top-right menu (☰): project schematic, personal loans, storage locations, remove-from-stock, log out.
- "Personal loan" button: check out equipment to a person for traceability, independent of any project.
- "Schematic" button: drag-and-drop technical diagram per project, connect components with wires,
  zoom (ctrl/cmd + scroll, centered on the cursor), fit-to-view, and split a box into segments.
  Layout/connections/splits are stored server-side so every collaborator sees the same diagram.
- Each item can have a photo (add/edit form → Photo field), shown as a thumbnail in the table.

## Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `3000` | Server port |
| `DATA_DIR` | repo root | Where `data/db.json` and uploaded photos (`uploads/`) live. Point this at a persistent disk in production. |
| `APP_PASSWORD` | unset (no login wall) | Shared password for the whole team. Leave unset for local dev. |
| `SESSION_SECRET` | dev default | Used to sign the session cookie. Set a random value in production. |
| `NODE_ENV` | unset | Set to `production` to require HTTPS-only session cookies. |

## Deploying to Render

The app needs a **persistent disk** — Render's default filesystem is wiped on every deploy, which
would lose the inventory data and uploaded photos. This guide uses Render's paid "Starter" plan
(the free tier doesn't support persistent disks and sleeps when idle, which breaks logins).
Approximate cost: ~$7/month for the web service + ~$0.25/GB-month for the disk (check current
pricing on Render's site before committing, since it's a recurring charge).

1. Push this repository to GitHub (or GitLab/Bitbucket).
2. In the Render dashboard, choose **New > Blueprint** and point it at the repo — it will read
   `render.yaml` in this repo and preconfigure the web service, the 1GB persistent disk mounted at
   `/data`, and the `DATA_DIR`/`NODE_ENV` env vars automatically.
   - Alternatively, create a **New > Web Service** manually: build command `npm install`, start
     command `npm start`, then add a Disk (mount path `/data`, 1GB) under the service's Disks tab.
3. When prompted, set the `APP_PASSWORD` env var to whatever password you want the team to share
   (marked `sync: false` in the blueprint, so Render will ask for it rather than committing it to
   the repo). `SESSION_SECRET` is auto-generated by the blueprint.
4. Deploy. Once live, share the Render URL and the password with your collaborators.
5. Keep the instance count at **1** (no autoscaling) — the app assumes a single Node process for
   its file-based storage.

To roll back to no-login access on Render (not recommended for a shared deployment), remove the
`APP_PASSWORD` env var.

## Deploying on your own Raspberry Pi (Cloudflare Tunnel)

An alternative to Render: run the app on a Pi you already own and expose it with
[Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/)
instead of paying for hosting. The app is light enough for any Pi (3/4/5), and storage is simpler
than on Render — the SD card is already persistent, no separate disk to configure.

**Why a tunnel instead of port-forwarding:** `cloudflared` (a small daemon you run on the Pi) opens
an *outbound* connection to Cloudflare's network and Cloudflare routes traffic to it. You never open
an inbound port on your router or expose your home IP — there's nothing for a port scanner to find.
Cloudflare also terminates TLS for you, so the app gets HTTPS for free.

**What it does *not* protect against:** the app itself is still the attack surface behind the
tunnel. A shared password can be brute-forced if someone finds the URL, and the Pi/Node app still
need routine OS updates. See the hardening step at the end — it closes this gap.

### 1. Prepare the Pi

```bash
# on the Pi, with Node 18+ installed
git clone <your repo url>
cd InventoryApp
npm install
APP_PASSWORD=<choose a password> SESSION_SECRET=<random string> NODE_ENV=production npm start
```

Confirm it works at `http://<pi-local-ip>:3000`, then stop it (Ctrl+C) and set it up as a service so
it survives reboots and crashes.

First, find the absolute path to `node` on this machine — systemd services don't load your shell's
`PATH`, so `npm`/`node` must be referenced by their full path or the service fails silently:

```bash
which node
```

Create the service file:

```bash
sudo nano /etc/systemd/system/inventory-app.service
```

```ini
# /etc/systemd/system/inventory-app.service
[Unit]
Description=Studio inventory app
After=network.target

[Service]
WorkingDirectory=/home/pi/InventoryApp
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=5
Environment=PORT=3000
Environment=APP_PASSWORD=<choose a password>
Environment=SESSION_SECRET=<random string>
Environment=NODE_ENV=production
User=pi

[Install]
WantedBy=multi-user.target
```

Replace `ExecStart` with whatever path `which node` printed, and `WorkingDirectory`/`User` with your
actual clone path and username. In `nano`: paste, then `Ctrl+O`, `Enter` to save, `Ctrl+X` to exit.

If you'd rather keep `npm start` in `ExecStart`, add an explicit `Environment=PATH=...` line covering
the directory `which node` printed — `npm` is itself a script that needs that `PATH` to find `node`,
which systemd doesn't provide by default (a common cause of "it worked in my terminal but not as a
service").

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now inventory-app
```

Check it's running, and watch logs live (`Ctrl+C` to stop watching, doesn't stop the service):

```bash
sudo systemctl status inventory-app
```

```bash
journalctl -u inventory-app -f
```

After pulling code updates (`git pull`), restart the service to pick them up:

```bash
sudo systemctl restart inventory-app
```

The `Environment=` values in this file (including the password) are readable by anyone with root
access to it — fine for an internal tool, but tighten permissions if you want to be stricter:

```bash
sudo chmod 600 /etc/systemd/system/inventory-app.service
```

### 2. Try it first without a domain (optional)

Cloudflare also offers a free **Quick Tunnel** that needs no domain, no DNS setup, and no account
configuration — good for confirming the whole pipeline works before buying anything:

```bash
cloudflared tunnel --url http://localhost:3000
```

(Install `cloudflared` first — see step 4 below for the install commands, then come back to this
one-liner.) This prints a random `https://<random-words>.trycloudflare.com` URL in the terminal.
Open it from outside your home network (e.g. your phone on cellular data, Wi-Fi off) to confirm it
reaches the app.

Quick Tunnels are for temporary testing, not daily use: the URL changes every time the tunnel
restarts, and you can't add the Cloudflare Access hardening (step 5 below) on top of it since that
needs a real domain. Once you're confident the pipeline works, get a domain (often just a few
$/year for common TLDs — not necessarily an expensive purchase) and continue below for a stable
link your team can bookmark.

### 3. Add your domain to Cloudflare

You need a domain with Cloudflare as its DNS provider (the free plan is enough). If it isn't already,
add it in the Cloudflare dashboard and update your registrar's nameservers as instructed there.

### 4. Install and configure `cloudflared` on the Pi

```bash
# ARM build — see https://pkg.cloudflare.com for the current install command for your OS
# Add cloudflare gpg key
sudo mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null

# Add this repo to your apt repositories
# Stable
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' | sudo tee /etc/apt/sources.list.d/cloudflared.list
# Nightly
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://next.pkg.cloudflare.com/cloudflared any main' | sudo tee /etc/apt/sources.list.d/cloudflared.list

# install cloudflared
sudo apt-get update && sudo apt-get install cloudflared
```

Create `~/.cloudflared/config.yml`:

```yaml
tunnel: studio-inventory
credentials-file: /home/pi/.cloudflared/<tunnel-id>.json

ingress:
  - hostname: inventory.yourdomain.com
    service: http://localhost:3000
  - service: http_status:404
```

```bash
cloudflared tunnel route dns studio-inventory inventory.yourdomain.com
sudo cloudflared service install
sudo systemctl enable --now cloudflared
```

Visit `https://inventory.yourdomain.com` from outside your home network to confirm it works.

### 5. Recommended hardening: Cloudflare Access

The app's shared password is the only thing standing between the internet and your inventory once
the hostname is known. Add a second layer, free for small teams, via Cloudflare **Zero Trust →
Access → Applications**: create an application for `inventory.yourdomain.com` and restrict it to
your collaborators' email addresses (they'll get a one-time login code by email before ever
reaching the app's own login page). This means even a leaked or guessed app password isn't enough
on its own.

Also keep the Pi's OS updated (`sudo apt update && sudo apt upgrade`), avoid exposing SSH directly
to the internet (tunnel it too, or keep it LAN-only), and treat the studio's power/internet
reliability as the deployment's main availability risk — there's no automatic failover like Render
provides.
